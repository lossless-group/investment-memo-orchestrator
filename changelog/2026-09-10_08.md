```
A Tauri app launched from Finder gets /usr/bin:/bin:/usr/sbin:/sbin. The
sidecar inherits it, shutil.which("claude") returns None, and every model call
from the desktop app fell back to the metered API — including all twenty-nine
routed the same day. `bun run dev:native` inherits the terminal's PATH, so it
never reproduces in development.
```

## Why care?

Yesterday and today, twenty-nine modules were moved onto a provider layer that
tries a Claude Code subscription seat before billing API credits. Seven
changelog entries counted the number down from twenty-four call sites to zero.

**All of it was inert in the desktop app.**

`cli_available()` was `shutil.which("claude") is not None`. `shutil.which`
searches `PATH`. A macOS application launched from Finder does not inherit a
login shell's `PATH` — it gets the system default, `/usr/bin:/bin:/usr/sbin:/sbin`,
and `claude` is not there. It is at `/opt/homebrew/bin/claude` here, at
`~/.local/bin` or `~/.bun/bin` elsewhere.

`sidecar.rs` spawns the FastAPI process through `tauri-plugin-shell` with no
environment manipulation, so it inherits that `PATH` exactly. Measured:

```
$ env PATH=/usr/bin:/bin:/usr/sbin:/sbin python -c \
    "import shutil; print(shutil.which('claude'))"
None
```

`cli_available()` → False → the API branch → metered, every call, on a machine
with a working logged-in seat.

**And `bun run dev:native` starts Tauri from a terminal**, which has
`/opt/homebrew/bin` on `PATH`. The sidecar inherits it, the lookup succeeds, and
the bug is invisible in development and present in every shipped build. No
amount of running the app locally surfaces it.

`claude_binary()` now resolves `MEMOPOP_CLAUDE_BIN` → `PATH` → a sweep of known
install locations, and `_via_cli` invokes the resolved absolute path rather than
the bare name, because `PATH` is exactly what is missing where this matters.

Verified at the realistic shape — real user session, GUI `PATH`, **no API key**:

```
LLM provider: Claude Code CLI (subscription seat) at /opt/homebrew/bin/claude
elapsed=2.9s  ok=True  provider=cli  text='SIDECAR-OK'
```

Written up as [[The-Sidecar-Cannot-See-The-Claude-CLI-On-PATH]]. One note from
diagnosing it: the first probe used `env -i`, which strips the user session and
fails differently (`Not logged in`). That sent the diagnosis sideways for a
minute. A Finder-launched app has a real session — it just has a short `PATH`.
**Simulate the environment you actually ship into, not a harsher one.**

## Brandfetch supplies what the model used to guess

`src/server/brand_fetch.py` asked Claude to read a firm's website and infer its
colors, fonts and logos from HTML and CSS. Brandfetch publishes those as data:

| Config field | Was | Now |
|---|---|---|
| `colors.accent` / `text_dark` / `background` | guessed from CSS | `colors[]` typed `accent`/`dark`/`light` |
| `fonts.header_family` / `family` | guessed from CSS | `fonts[]` typed `title`/`body` |
| `logo.light_mode` / `dark_mode` | scraped `<img>` URLs | `logos[]` by `theme`, SVG preferred |
| `company.name` | inferred from copy | `name` |

The model is now asked only for what Brandfetch does not carry — tagline, legal
entity, the dark-mode palette, the Google Fonts URL — and is shown what is
already known so it does not contradict it. **Brandfetch wins every key it
supplies.** That is the point: a brand config copy-pasted between firms with its
colors never updated is a failure this repo has shipped, and a hex from a brand
data API is checkable in a way a hex a model read off a stylesheet is not.

This also removed the last direct Anthropic client. The old path was a tool-use
loop — Claude calling `fetch_url` across up to eight turns — which `complete()`
cannot express. With the hard-to-infer fields arriving as data, a single-shot
call over the homepage and `/about` is enough. That is genuinely less adaptive,
and it is the trade that lets this module use the seat like everything else.

**Zero modules under `src/` construct an Anthropic client.** The generated
reference says so, and the test that used to be a ratchet is now absolute:
`KNOWN_BYPASSING` is empty, with a second test asserting it stays empty.

## An API is not automatically right

The first live run produced `fonts.family: "var(--font-body)"`.

Not a model error — **Brandfetch returned it**. Its scraper reads `font-family`
declarations without resolving custom properties, so a site built on CSS
variables yields `var(--font-display)` with `origin: "custom"` and no weights.
`humain.vc` is a live example. Written into a brand config that produces
`font-family: var(--font-body)` in the export, which resolves to nothing and
silently falls back to the browser default.

Rejected now, along with `inherit` / `initial` / `unset` / `none` and anything
still carrying CSS punctuation; a stack like `'Inter', Helvetica, sans-serif`
yields `Inter`. The key then goes **absent**, the model is asked for it, and a
human reviews the answer.

On the re-run the model could not derive fonts from the React shell either — and
said so in `confidence_notes` rather than inventing them, which is §5 and §7
doing their job.

*"It came from an API" is a reason to trust data more, not a reason to stop
checking it.*

## Suite

**479 passed, 1 skipped** — up from 434. Nine tests on binary resolution
(including that `_via_cli` uses the resolved path), thirty-five on the
Brandfetch client and its mapping.

## What is still open

- **Windows.** The fallback install list is macOS/Linux-shaped, and the sidecar
  there runs `.venv/Scripts/python.exe`. Untested; `MEMOPOP_CLAUDE_BIN` is the
  escape hatch.
- **The adaptive fetch.** Brand extraction reads the homepage and `/about`. A
  firm that keeps its press kit at `/brand` will need a human to fill more gaps
  than the old loop would have.
- `BRANDFETCH_API_KEY` belongs in `.env.example` and `docs/SETUP.md`; it is
  optional, and the code degrades cleanly without it.
