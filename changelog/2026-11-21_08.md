```
feat(connector): Prepare the uploader: binaries with text, known blobs, and a check

The uploader extracts each binary's text with the connector's own reader and
writes materials/<id>.md, so the material is ready the way an add_materials
upload is; a binary with no text is recorded skipped with its reason.
gather_inputs() turns a ready material with no text file into a notice, so a
deal staged by the old uploader still walks through materials.brief.

fold_imported_blobs.py hashes the old imported/ keys on the server and copies
each distinct hash to blobs/<sha256> once, printing the hash list. The uploader
takes it with --known-blobs and stages none of those bytes; apply_upload.py
refuses if one of them is not in the bucket. check_upload.py snapshots each deal
on the server and compares it with the local folder.

Also included: CONN-UPL-03 in the spec and plan, the issue resolved, plan steps
0, 1 and the check-script part of 4 ticked.
```

## Why Care?

The uploader was written but couldn't safely run. An imported deal that wasn't finished stopped at its first step: every binary was recorded `ready` with no text file behind it, so `next_step` reached `materials.brief` and failed with `artifact_not_found`. The first firm's bucket also holds 901 `imported/…` keys from the October import, and the uploader would have sent all those bytes again. And nothing could say, after an upload, whether the server matched the local folders.

## What's New?

- **Binaries arrive with their text.** `scripts/upload_firm.py` runs each binary through `src/connector/materials/extract.py`, the reader `add_materials` uses on the server, once per distinct hash. A readable file is `ready` with `materials/<material_id>.md`. An image or a file with no text layer is `skipped` with the reason, plus a `materials.extract` skip (`material_unreadable`), the record the server writes for an unreadable upload. The report says how many per deal had no text.
- **Why not leave them `queued` for the server.** Nothing on the server picks up a `queued` material: extraction jobs live only in the process that took the upload. The materials sweep would mark them all `skipped` at the next restart, or 30 minutes after they were added.
- **A missing text file is a notice, not an error.** In `src/connector/flow.py`, `gather_inputs()` gives a ready material whose text file is missing as an input that says so, and the walk goes on.
- **`scripts/fold_imported_blobs.py`** runs on the server, reading the script from stdin over `railway ssh`. It hashes every `imported/…` object, copies each distinct hash to `blobs/<sha256>` unless that key exists, prints the hash list on stdout and its progress on stderr. `--dry-run` copies nothing. It never deletes or changes an `imported/` key.
- **`upload_firm.py --known-blobs <file>`** records those files like any other binary (manifest entry, material, bucket key) but stages none of their bytes. `plan.json` lists the ones it relied on as `known_blobs`, and `apply_upload.py` refuses, before its backup, if any is missing from the bucket.
- **`scripts/check_upload.py`.** `snapshot <firm>` runs on the server and prints each deal's sections, drafts, compiled label and materials (with whether each text file and bucket object exists) as JSON. `compare io/<firm> --snapshot <file>` runs on the laptop and reports per deal the compiled label against the newest local `7-`/`6-` memo, the sections against the local outline, and the materials against `binaries-on-server.yaml`. It exits 1 if anything differs.
- **Tests.** Ten new tests in `tests/test_upload_firm.py`: CONN-UPL-01 (four), CONN-UPL-02 (three), and CONN-UPL-03 (two, a new spec ID).

## What Isn't Tested

- **Nothing has run against the server or a real bucket.** The fold script, the check snapshot and `--apply` are tested on local folders and a local bucket. Whether `railway ssh` passes stdin and stdout through cleanly enough for the hash list and the JSON snapshot is assumed from how `--apply` already uses it, not checked.
- **Extraction on a real data room.** The tests extract a two-page PDF and an unreadable image. A firm's data room has hundreds of files, some scanned, and the reader's OCR fallback may make staging slow. That will show at step 2.
- **The S3 side of the fold script.** It reads each object into memory, which is fine for slimmed data rooms, and it hasn't been run against S3.
- **Duplicate material ids.** The same bytes at two paths in one deal still get the same `material_id`, so `deal.json` holds two records with one id. That predates this change and is left as found.
