## Why care?

A live real-Claude run (CONN-PLUG-02, Haiku 5.5) did everything right except
one thing. When `next_step` listed `research.sources` in
`skipped_since_last_call`, Claude went straight on to drafting and never told
the partner. The skill already said to tell the partner, and an earlier run did,
so the behaviour wasn't reliable. A partner who isn't told about a skipped step
doesn't know their memo is missing something.

## What landed

**`tell_partner` on `next_step`** (API 1.3.0, additive). Whenever
`skipped_since_last_call` isn't empty, `next_step` returns one plain sentence
for Claude to pass on word for word. It is `null` when nothing was skipped, and
it comes with the `done` answer too. The wording rules:

- `Skipped: <step title> (<sections>), because <why>.` The step title comes from
  the registry. Section names appear only for steps that run once per section.
- If one step is skipped for several sections in a row for the same reason, those
  skips share a clause, for example `Add tables to a section (Overview, Market,
  Team)`. Different skips get one clause each, joined by semicolons, so the
  result is still one sentence.
- `<why>` comes from the skip's code, not from its stored reason, because the
  server's own reasons already repeat the step title:
  - `step_disabled`: "it is turned off on this server".
  - `step_failed`: "it failed on MemoPop's side".
  - A material that can't be read: "a material could not be read" plus the
    error in quotes.
  - Claude's own skip: `it was skipped with the reason "<reason>"`.
- Free-text reasons are put on one line: whitespace is collapsed, trailing
  punctuation is dropped, double quotes become single quotes, and the reason is
  cut at 200 characters.

**The instruction carries the notice too.** On the call that reports a skip,
`instruction` begins with "Before you start this step, send the partner this
line, word for word, as its own short message: …". Claude fails this way by
going straight to the step's work, and the instruction is the text it reads to
do that work. With the notice there, a model that skims past the new field
still reads it. It costs nothing on later calls: skips are reported once, so
the next call for the same step returns the plain instruction. CONN-STEP-10
tests both.

**The skill** keeps its one-line rule for `skipped` and adds one sentence: if
`next_step` returns `tell_partner`, send it to the partner word for word, as its
own short message, before you do that step's work. CONN-PLUG-01 gains a rule
that checks for this. The existing rules are unchanged, and the scattered-words
guard text gained the new rule's words so the guard still covers it. The plugin
version is now `0.1.1`.

**The real-Claude harness.** The JSON report now keeps every message whole
instead of cutting it at 400 characters, and each `next_step` event that
carries a `tell_partner` shows it. The skip check accepts a line that relays the
server's sentence (ignoring markdown and quotes), or a line that names the
skipped step and uses a skip word, as before. It still fails when no message
after the skip mentions it. The offline scripted model now relays
`tell_partner`. A `paraphrase_skip` variant shows that telling the partner in
Claude's own words also passes, and `ignore_skip` is still caught.
