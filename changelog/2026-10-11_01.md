```
fix(check): Keep the Mac awake for the whole check ladder
test(connector): Fail any test whose background work outlives it, and report a sleeping machine
```

## Why care?

`bash scripts/check.sh` seemed to hang locally: pytest at 100% CPU for 30 to 80
minutes, a few tests done, and no faulthandler dump. CI on Linux was green. The
leading theory was background threads leaking across tests and slowing coverage's
tracer. The measurements don't support that theory. The machine was asleep.

## The cause, with evidence

The laptop runs on battery with `pmset` `sleep 1`, so it idle-sleeps after one
minute when nothing holds a sleep assertion. Claude Code holds one (`caffeinate`)
only while the agent is busy. When an agent ends its turn to wait on a background
`check.sh`, the assertion lapses and the Mac sleeps, with pytest frozen inside it.

From `pmset -g log`, for each of the VP Eng's stalled runs overnight:

| Run (local time) | Wall | Asleep | Awake |
|---|---|---|---|
| check.sh, plan 2 merge (23:15) | 14.2 min | 13.6 min | 0.7 min |
| check.sh rerun (00:00) | 32.1 min | 32.0 min | 0.1 min |
| `pytest -v -x tests`, the "79 minutes at 100% CPU" (00:48) | 79.1 min | 78.0 min | 1.1 min |
| single fact_check test with faulthandler (02:38) | 57.3 min | 56.5 min | 0.8 min |
| connector folder, `faulthandler_timeout=120` (03:51) | 34.9 min | 34.9 min | 0.1 min |
| `--collect-only` "took over two minutes" (05:25) | 16.5 min | 16.5 min | 0.0 min |
| the same tests, in the morning (09:31) | 1.0 min | 0.0 min | 1.0 min |

This explains each symptom:

- **The run makes almost no progress.** It only runs during brief dark wakes.
- **ps shows 100% CPU.** The CPU figure is averaged over time the machine was awake.
- **faulthandler never fires.** Its timer runs on the monotonic clock, and that
  clock stops while the machine sleeps, so no test ever reaches 120 s of it.
- **Every test passes alone in about 10 s.** Those runs happened while someone
  was at the keyboard.
- **CI is green.** CI runners don't sleep.

Reproduced here: the full suite under Python 3.11 took 8.2 minutes of wall time,
but pytest reported 206.6 s. In between, `pmset` logged `Entering Sleep state due
to 'Idle Sleep'` six seconds after the session's caffeinate exited. A test that
takes 1 s took 220 s of wall time. With coverage on, the same suite took 197 s
while the machine stayed awake, under both Python 3.13 and 3.11. Coverage, its
HTML report, WeasyPrint, and jj all ran at normal speed.

**The thread theory is ruled out.** We counted `threading.enumerate()` at every
teardown. No test left more than one connector thread alive. The materials pool
kept three idle workers, which block on a queue and use no CPU. The one real
leak was small: CMP-03's compile worker was still recording to jj when its test
ended.

## What landed

**`check.sh` keeps the Mac awake.** On macOS it re-executes itself under
`caffeinate -i -s` for the whole ladder. To check this, we ran it with the
session idle. At 10:04:05 the session's own caffeinate lapsed, which is the
moment that put the machine to sleep earlier. This time check.sh's caffeinate
held until the run finished, and there was no sleep. A closed lid on battery
still sleeps; `caffeinate` cannot prevent that.

**The suite reports when the machine slept** (`tests/conftest.py`). Each test
and the whole session compare the wall clock with the monotonic clock. When a
test's wall time exceeds its awake time by 10 s or more, a `[suite clock]` line
names the test right away. The session summary also prints a banner with the
total. This is a report, not a failure: the results are still valid.

**No background work outlives its test.** The materials pool now tracks in-flight
jobs (`pipeline.wait_idle(timeout)`), and the compile tool tracks its workers,
including ones detached past the budget (`compile.wait_for_workers(timeout)`). An
autouse fixture in `tests/connector/conftest.py` waits up to 30 s for both after
every test. If anything is still running, the test errors and names what's left.
The fixture depends on `monkeypatch`, so it waits before the test's patches are
undone. Otherwise a late materials job could fetch through the real transport.
We confirmed the guard fails a test that leaves a job running.

## Decisions a reviewer should know

- **Coverage is unchanged.** `addopts`, the HTML report, and the branch coverage
  stay as they were. The measurements gave no reason to change them.
- **No `pytest-timeout`.** It would not have caught this. Its timers don't
  advance while the machine sleeps, and every test was fast in awake time. Where
  its timers do count sleep, it would turn a valid run red.
- **The sleep notice warns but does not fail the run.** Failing a correct run
  because the laptop slept would be a false red.

## Results

- **`check.sh` before:** it never finished overnight. Runs were killed after 14
  to 80 minutes of wall time, with 0.1 to 1.1 minutes of that awake.
- **`check.sh` after:** 191 s and 189 s back to back, plus 205 s with the session
  idle. All three runs exited 0 with 687 passed and 12 skipped. Two tests are new
  in `tests/connector/test_background.py`.
- **The ledger:** 56 green, 2 gated, 0 red, 0 missing across every plan, and
  54/54 green for the active plans.

## What was not tested

We did not test a closed lid on battery. macOS sleeps then regardless of
assertions; the `[suite clock]` line will say so. We tested the sleep notice's
arithmetic, not a real sleep during the check, because forcing the operator's
machine to sleep was off the table.
