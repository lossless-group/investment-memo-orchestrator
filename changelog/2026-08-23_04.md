```
new(timeseries): time-series_analyst — the agent that owns the company grid
new(timeseries): periods — any source date format in, ISO 8601 out
new(timeseries): timeline — one origin per company, counts derived from it
new(spec): Company-Timeline-And-Month-Indexed-Time-Series
new(reminder): Use-Tidyverse-Conventions-to-Normalize-Timeseries-Data-Across-Files
new(tests): 29 covering period parsing, count arithmetic, and file layout

**Status: first draft, unexercised.** The 29 unit tests pass and the agent has
been driven by hand against constructed observations. It has never seen a real
dataroom, because nothing feeds it yet — the financial extractor still returns
its own dict shape and the chart collector captures a chart's axes without
reading its plotted points. Treat every design decision below as untested against
real documents.

Financials, KPIs, cap tables, and charts all describe the same company over the
same period. Left to themselves each extractor would write its own files, and
each would get the convention wrong in a different way — a different origin, a
different date format, a different idea of what a row is. So none of them writes
a time series. They emit `Observation` records and offer origin evidence; one
agent establishes the origin, computes the counts, and writes the files.

**The origin belongs to the company, not to the document.** This is the whole
mechanism and the easiest thing to get wrong. A spreadsheet beginning January
2024 does not restart the count. With a February 2023 origin it lands on
`month_count` 12, because month 01 is the earliest month the *archive* can
evidence, not the earliest month that source happens to cover. Two spreadsheets
spanning different ranges, a deck's chart, and a board pack's KPI table then
describe the same company at the same offsets and match on the count.

Origin evidence is ranked by earliness first, strength second. A charter dated
three years before the first spreadsheet wins, and the data then starts at
`month_count` 37 — which is the useful answer, because it says plainly that three
years are undocumented rather than quietly redefining the company's history to
begin when its bookkeeping did. Every alternative considered is recorded, since a
deck claiming one founding date while the paper shows another is a diligence
finding rather than noise.

**Dates are ISO 8601 or they are wrong.** Source documents spell periods every
way there is: `Feb-23`, `Q1'24`, `2/1/2023`, `FY2024`, `as of 2023-02`. All of
them parse; none of those forms reaches a file. This is disambiguation rather
than tidiness — `03/04/2023` is March 4th to an American and April 3rd to
everyone else, and a two-digit year loses its century. What the source said is
kept once in `source_raw_period` as provenance, so an ambiguous parse can be
checked instead of trusted.

Slash forms are settled per *column*, not per value. `03/04/2023` on its own is
unresolvable and is flagged ambiguous. In a column also containing `13/04/2023`
it is not: 13 cannot be a month, so the document is day-first and every value in
it reads the same way.

**Three grids, never interpolation.** Data is written to the grid matching the
periodicity it was stated in — a Q2 figure is a Q2 row, not three invented
months. `month_count`, `quarter_count`, and `year_count` all run from the same
origin, with the coarser grids beginning at the period *containing* it so
calendar alignment survives. Rolling up from finer to coarser is allowed and
marked; splitting coarser into finer is forbidden, because it invents a monthly
seasonality nobody reported and is then indistinguishable from data.

**Long, not wide — for a stated reason.** "Tidy" does not mean "long", and the
first draft of the spec conflated them. Wickham's rule is that each *variable*
gets a column, and for a fixed known metric set a wide table is the tidy one.
Long is right here because the metric set is **open**: every document reports
whatever it reports, names are not canonical, and new documents arrive
continuously. When the variables are not known in advance, `metric` is the
variable — and a wide file built from an open metric set puts source-specific
vocabulary in the header row, which is Wickham's messy-data problem #1.

**Nothing is reconciled.** Where two documents disagree about a period, both are
written and the divergence is left visible. One file per source document, never a
merge; a restatement is a new file named for the document that stated it. Metric
names are recorded as the source spells them, because mapping `ARR` to `Annual
Recurring Revenue` is a judgment that belongs where a person can see and revise
it. `basis` — actual, projection, restated, chart_read — is never lost, since
plotting a projection as history is the worst failure available here.

**What it deliberately does not do:** analysis. No filling, no reconciliation, no
derived metrics, no normalization. A cap table is written sparse — ownership
changes at financing events, every six to thirty-six months — and forward-filled
in analysis rather than on write, because a filled row on disk is
indistinguishable from a stated one and would assert an ownership percentage for
a month no document covers.

**Also included:** the reminder and the spec that state the conventions, so the
next extractor author has something to read that is not source code.

**Next, and required before this is worth anything:** `financial_extractor` and
the unbuilt KPI extractor emit `Observation`s instead of bespoke dicts, and the
chart collector grows a temporal branch — a chart with a time axis should put its
plotted points on the grid under `basis: chart_read`, flagged because a value
read off a plot is weaker evidence than a stated figure.
```

## Shape of the output

Per company, beside the existing analysis artifacts:

```
<company>/
├── timeline.yaml            ← the origin, its basis, its evidence, alternatives
└── 7-timeseries/
    ├── 20240115_Company_OperatingModel--Actuals--Monthly.csv
    ├── 20250203_Company_Model--Projections--Monthly.csv
    ├── 20250924_Company_Financials--Quarterly.csv
    ├── 20231112_Company_CapTable--Snapshot--By-Holder-SecurityClass--Monthly.csv
    └── README.md            ← gaps, roll-ups, ambiguous dates, and how to read them
```

A row, long-format, time columns first:

```csv
month_count,quarter_count,year_count,date,year_month,year_quarter,...,metric,value,unit,basis,is_rolled_up,is_gap_fill,source_document,source_detail,source_raw_period
12,4,2,2024-01-01,2024-01,2024-Q1,...,revenue,125000,USD,actual,False,False,20240115_Company_OperatingModel.xlsx,"Sheet 'P&L', row 14",Feb-23
```

Juxtaposition needs no code of its own — it is a pivot on `source_document`:

```
source_document   20240115_…--Projections   20250203_…--Actuals
month_count
12                                 125000                118000
13                                 141000                152000
```

## Why this exists

Because a memo that cites a growth rate should be able to say which document
claimed it, and a reader who wants to know whether a company hit its own
projections should be able to see the projection and the outcome on the same
axis. Neither is possible when each extractor invents its own shape, and both are
trivial once every number carries the same index.
