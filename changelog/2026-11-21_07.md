```
feat(connector): Edit a finished memo's sections, final draft, and outline

edit_section saves a wording change to a section as a new version, with no
revision and no research reopened. edit_final edits the compiled memo so the
partner sees it now, then makes the same edit in the section it falls in, so
the next compile reproduces it. get_outline and edit_outline change the
outline one memo uses, on its own pinned copy; apply_to firm changes the
firm's outline and lists the deals on it without changing any.

compile refuses with final_has_untracked_edits when the latest final has
changes its sections don't produce, listing each by section, unless
discard_untracked is true. API 1.8.0.

Also included: edit_not_placed error code, the routing table in five tools'
docs and the server instructions, three playbooks rewritten for the tools,
research.section v2 states the two-task rule, spec rows and plan ticks.
```

## Why Care?

The spec's Plan 9 says where a partner's change goes: sources and facts into research, wording into the section, "just edit the memo" into the final draft, carried back. Until now only the first route existed. Everything else went through `start_revision`, which reopens the whole section walk for a typo, and a change made to the final draft by hand was overwritten on the next compile without a word.

## What's New?

- **`edit_section`** (`POST /v1/deals/{deal}/section-edits`). `edits` (old/new pairs, each matching exactly once, applied in order) or a whole `text`. It writes a new version of the artifact compile reads the section from: the latest of the draft and its enhancements, or the revised summaries for a bookend section they replace. It refuses with `revision_open` while a revision covers the section, and `section_not_drafted` before a draft exists. Several stack before one compile.
- **`edit_final`** (`POST /v1/deals/{deal}/final-edits`). Each `old` must match the latest compiled final once. The edit is placed by the final's level-2 headings, matched to the sections compile assembled. It must fall inside one section's text and match that section's text once, else `edit_not_placed` names the edit and why (spans sections, sits in the title, contents or consolidated citations, or the section words it differently, usually citation numbers). Nothing is saved unless every edit places. The edited final becomes the next compiled version with a bumped label and fresh exports; each section touched gets a new version; the pairing goes in the deal's `final_edits`. `facts_changed: true` makes `next_hint` send Claude to `start_revision` for the research.
- **The compile guard.** Every compiled version now keeps `compiled/<v>/from-sections.md`, what the sections produced for it. Before compiling, the stored final (F) is compared with that (B) and with what the sections produce now (C), section by section, with citation numbers, citation lists and whitespace normalised. A section whose F block equals B was not edited in the final; one that equals C was edited and carried back. Anything else is untracked and stops the compile with `final_has_untracked_edits`. Citation definitions are compared the same way as one more block. `discard_untracked: true` compiles anyway. A memo imported from a local run has no B: the first `edit_section`, `edit_final` or `start_revision` writes it from the sections as they were, and until then it is rebuilt.
- **`get_outline`** (`GET /v1/outlines`) and **`edit_outline`** (`POST /v1/deals/{deal}/outline-edits`). Ops `add_section`, `update_section`, `move_section`, `remove_section`. The deal's pinned copy is written once from the sections the deal has, as `<template>--<deal>` in the firm's outlines, and the deal's `template` points at it. Every section gets an explicit `filename`, so keys never shift. An added section is handed out by `next_step`; a section whose description or questions changed is marked (`outline_seq`) so its research, draft and enhancements count as not done until saved again (a two-line change in `flow.is_done`). `apply_to: firm` writes the firm's outline (copying a MemoPop one first) and returns `deals_using`.
- **Docs.** The routing table is in the docs of `start_revision`, `edit_section`, `edit_final`, `edit_outline` and `compile`, and the MCP server's instructions name the tools. `edit-wording`, `just-edit-the-memo` and `change-the-outline-for-this-memo` now use the tools instead of the revision fallback. `research.section` (v2) states that research and the rewrite are two tasks.
- **Tests.** `tests/connector/test_edit_tools.py`, CONN-EDIT-01 to 06, seven tests.

## What Isn't Tested

- **Imported memos against the guard.** No test compiles a deal whose final came from a local run. Its final was assembled by the local pipeline (its own contents block, citation format, deck images) and often edited by hand, so the guard will very likely refuse its first server compile with many differences. That is the guard doing its job, since compiling would drop them, but the noise on real firm data is unmeasured; `io/` is not readable here.
- **The lazy baseline.** That `edit_section`, `edit_final` or `start_revision` writes `from-sections.md` for an imported memo is not covered by a test.
- **`facts_changed`**, `move_section`, `remove_section`, `edit_section` with `text`, an outline change to a section's questions showing in `next_step`, and edits to a section compiled from `enhance.summaries` have no tests of their own.
- **Whitespace-only edits** to a final are normalised away, so the guard doesn't see them and compile overwrites them.
- **A real Claude choosing the right tool** from the routing table.
- **Not redeployed.** The plan's last box (regenerate the docs and redeploy) is for the VP Eng.
