```
feat(connector): Serve a deal's latest compiled memo to the firm's site

A firm's site can now read a deal's latest compiled memo at request time,
so a partner who compiles in Claude sees the change on the LP page after
a refresh. GET /site/v1/firms/{firm}/deals/{deal}/memo returns the
markdown, version, label, compile time, and signed export links, behind a
per-firm site key from MEMOPOP_SITE_KEYS.

Site keys are separate from partner auth: a site key can't call the tools,
and a partner key is refused on the site route. Another firm's key is 403,
no key 401, a deal never compiled 404.

Local image paths in memos imported from local runs become signed links to
the binaries the uploader put in the bucket; anything unmatched is listed
in images_unresolved. compile returns site_url when firm.json maps the deal
to a page.

Also included: the spec's Site read endpoint subsection and the plan's
image finding.
```

## Why Care?

Partners at a firm edit memos by chatting with Claude, but they only trust it once they see the change where the memo lives: the firm's investor area. Until now a memo reached that page by a hand-run pull script, a commit, and a deploy. This is the orchestrator's half of the firm-site pattern (`astro-knots/context-v/specs/Firm-Sites-Show-the-Latest-Memo-from-MemoPop.md`): the site can now fetch the latest compile itself.

## What's New?

- **`GET /site/v1/firms/{firm}/deals/{deal}/memo`** in `src/connector/site.py`, mounted beside `/v1/files`. It returns `markdown`, `version`, `label`, `compiled_at`, `company`, signed `html_url` and `pdf_url` (`null` when the export was never made, as for the uploader's imported version 1), and `images_unresolved`, with `Cache-Control: private, no-store`.
- **Site keys.** `MEMOPOP_SITE_KEYS` (`firm=key,…`) in `config.py`. One firm's key can't read another's (`403`). A missing or unknown key, or a partner's key, is `401`, and site keys are refused by the tools under `/v1/`. Reads and refusals are logged with firm and deal, never the key.
- **Images.** Memos compiled on the server carry no image files: the market-sizing diagram is an inline `data:` SVG, and deck images are only placed from `materials/deck-images.json`, which nothing writes yet. Memos the uploader imported from local runs point at deck screenshots and diagrams by local path, and the uploader put each of those files in the bucket as `blobs/<sha256>` with its `local_path`. The endpoint rewrites each matching reference to a signed link; when several runs have a file of the same name, the copy from the memo's own version wins. Hosted and inline images are left alone; unmatched local paths are left as written and listed.
- **`compile` returns `site_url`** when `firm.json` has `site_memo_url` (a pattern with `{slug}`) and `site_memo_slugs` maps the deal, and its `next` tells Claude to give the partner that link.
- **Tests:** `tests/connector/test_site.py`, CONN-SITE-01 to 04.

## Not Tested

- **Nothing against the deployed service or a real S3 bucket.** The tests use the local bucket and its HMAC-signed `/v1/files` links. On S3 the image links are presigned URLs; their content type is whatever the uploader set on the blob. On the local bucket a blob has no extension and is served as `application/octet-stream`.
- **Image matching against real imported deals.** The rewrite was tested on a synthetic deal shaped like the uploader's output, not on `humain-vc`'s imported memos. The reference shapes it handles were read off the local `io/` memos.
- **The site side.** No site has called the endpoint yet.
