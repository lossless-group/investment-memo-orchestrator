```
feat(connector): Serve the method from the server: playbooks, prompts, instructions

A connector added by URL gets no plugin skill, and Claude loads its tools only
when a request names MemoPop. The server now carries the method itself.

list_skills and get_skill (MCP and REST, read-only) serve six playbooks from
src/connector/skills/; an unknown name is skill_not_found with the names that
exist. Four MCP prompts (Edit a memo, Fix a citation, Change the outline for
this memo, Check the memo on the site) each name MemoPop and the playbook to
load. The server instructions open with editing finished memos, route each
kind of change, and name list_skills and whoami.

Also included: llms.txt and /docs list the playbooks and prompts; API
changelog 1.5.0; a paste-once getting-started prompt and onboarding email in
docs/operator/; next_step.py reformatted so black --check passes.
```

## Why Care?

In the first partner test, a partner who added MemoPop by URL asked Claude to fix a citation and Claude never reached MemoPop. A connector added by URL brings no skill, and Claude keeps its tools deferred until a request names the connector. Everything Claude needed to know lived in the plugin, which URL-added partners never install.

Now the method is on the server, the way event-hog serves its skills. A playbook edited in git reaches every partner on their next call.

## What's New?

- **Six playbooks** in `src/connector/skills/`, one markdown file each with `name` and `description` frontmatter: `fix-a-source-or-citation`, `rewrite-a-section-from-its-research` (the two-task rule: edit the research, then rewrite from exactly the research and the current draft), `edit-wording`, `just-edit-the-memo`, `change-the-outline-for-this-memo`, `compile-and-check-the-site`. Each ends with the tool to call.
- **`list_skills` and `get_skill`**, at `GET /v1/skills` and `GET /v1/skills/{name}` and over MCP, with full docs entries. New error code `skill_not_found`.
- **Four MCP prompts**, each with an optional `request` argument for what the partner typed.
- **Server instructions** open with "MemoPop holds this firm's finished investment memos", say where each kind of change goes, keep the step-by-step method, then name `list_skills`/`get_skill` and `whoami` for partners on more than one firm.
- **A getting-started prompt** partners paste once, with an onboarding email: `docs/operator/getting-started-prompt.md`.

## Not Tested, and Why

- **Four playbooks describe tools that don't exist yet.** `edit-wording` needs `edit_section`, `just-edit-the-memo` needs `edit_final`, `change-the-outline-for-this-memo` needs `edit_outline`, and `compile-and-check-the-site` needs compile's `site_url`. Each says so and tells Claude to use `start_revision` (or, for adding or removing sections, to tell the partner it can't be done yet). They will need rewriting when those tools land. The tests check that every playbook is served and ends naming a tool, not that the advice works.
- **`whoami` is named in the instructions but is not part of this change**; another plan builds it. Until it merges, Claude would find no such tool.
- **No real Claude has used any of this.** Whether Claude picks the right playbook from a request that doesn't name MemoPop, and whether the paste-once prompt gets past deferred tools, is the operator's retest (plan step 6).
- **Prompts in Claude's menu** are tested over MCP (`prompts/list`, `prompts/get`), not in Claude Desktop's UI.
