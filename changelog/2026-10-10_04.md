## Why care?

This is plan 6 of the connector spec (`context-v/specs/MemoPop-Connector-API.md`),
carrying out the decision *jj Versions Text, and a Save Snapshots to the Bucket*.
A partner never types a version-control command, but every research file and
draft they approve is now kept, version by version, and Claude can read an
earlier one back with `get_artifact`. When the partner asks for a backup,
`save_snapshot` writes the whole workspace to the firm's private bucket and
says how many files were added, changed, and removed since the last one.

## What landed

**One jj repository per firm** (`src/connector/history.py`). The repository is
made on the firm's first write with `jj git init --no-colocate` in the firm
root, plus a `.gitignore` that excludes the binary kinds (PDF, images, office
files, archives, media). After each saved artifact the server records exactly
one change containing just that artifact and its `deal.json`; content that
didn't change records nothing. The description is the one the tool passes, so
it names the step, deal, and section, for example
`research.section: deal fixture-co, section 01-overview, v1`.

**jj runs in a fixed environment.** Every call is a subprocess with
`-R <firm root>`, `JJ_CONFIG` pointing at a file the server writes, the author
fixed to `MemoPop <noreply@didi.sh>`, the operation host and user set to
`memopop`, and every inherited `JJ_*` and `GIT_*` variable dropped. A test sets
a leaky `JJ_CONFIG`, `JJ_USER`, and `JJ_EMAIL` and checks none of them reaches a
change. `snapshot.auto-track` admits text extensions only (`md`, `json`, `yaml`,
`txt`, `csv`, `html`, and a few more), so a binary never enters the working
copy even when the `.gitignore` misses its extension.

**Earlier versions are readable.** `get_artifact` with an older `version` used
to return `artifact_not_found`. History now walks the changes that touched the
artifact and returns it from the one whose `deal.json`, committed in the same
change, records that version. No change to `get_artifact` itself was needed.

**`save_snapshot` works** (`src/connector/tools/save_snapshot.py`). It writes
`snapshots/<UTC timestamp>-<label slug>.tar.gz` (for example
`snapshots/20261010T153012Z-before-ic-meeting.tar.gz`) to the firm's bucket,
with members under `<firm>/` and jj's `.jj/` included, and beside it
`snapshots/<snapshot_id>.manifest.json`: the id, label, time, sequence, the
previous snapshot's id, the archive's size and sha256, the latest jj change,
the three counts, and a sha256 per workspace file. The counts compare against
the previous manifest and cover the partner's files only, not jj's internals or
lock files. The response has the spec's fields plus `previous_snapshot_id`
(additive, and in the API changelog as 1.1.0). Its two docs examples now run
for real.

**Isolation.** Each firm's repository is rooted at its own directory and
nothing above them is a repository. A history read for a path outside the firm,
by absolute path or by `..`, returns nothing. Snapshots go to the firm's own
bucket, and symlinks are never archived or followed, so a link planted in one
firm's workspace can't pull another firm's file into its backup.

**Ledger.** CONN-HIST-01 to -05 were all RED and none missing at the test
commit; all five are GREEN now, with every plan 1 ID still GREEN (38 green, 0
red). The suite is 580 passed and 10 skipped; none of the skips is a history
test.

## Decisions a reviewer should know

- **A jj failure is logged, not raised.** Recording runs after the artifact is
  durably written, so reporting `down` would tell the client nothing was saved
  when it was, and the retry would be a no-op. The unrecorded diff stays in the
  working copy and the next save of that path sweeps it into its change.
- **No jj on the machine means no history, not no service.** `history_for`
  returns the no-op history and logs once. Production must have jj installed
  (plan 2's Dockerfile); `MEMOPOP_JJ_BIN` names the binary.
- **Only the given paths are committed.** Writes that don't call history, such
  as `next_step` marking a step handed out, stay in jj's working-copy change
  until the next save of that deal's `deal.json` carries them. The snapshot
  archives the working copy as it is, so nothing is lost from a backup.
- **The earlier-version test sits under CONN-HIST-01.** The spec has no ID for
  "get_artifact returns an earlier version". The test is marked CONN-HIST-01
  because the recorded change is what makes the version readable. A dedicated ID
  would be cleaner; that is the spec owner's call.
- **Test speed.** Each recorded save costs two jj calls (a diff, then a commit),
  about 120 ms on a laptop. Plan 1's paging test, which creates 105 deals, went
  from 0.5 s to 13 s, and the connector suite from 2 s to 27 s.

## What was not tested

The S3 bucket still has no test: snapshots were only written to the local
directory bucket, so a large archive through boto3 (one `put_object` of the
whole thing, held in memory) has never run against a real Railway bucket.
Nothing was deployed, and no jj other than 0.46.0 (laptop and CI) has run this
code. Concurrency is covered by design, not by a test: a thread lock plus an
`flock` per firm around every jj write, and a per-firm snapshot lock, but no
test races two saves or a save against a snapshot. A snapshot taken while
another deal's multi-file write is mid-flight can hold that deal's artifact
without its `deal.json` update, because only history writes are held off, not
every workspace write. Nobody has restored a workspace from a snapshot yet;
the tests open the archive and check its members, but no restore path or tool
exists. Workspaces that already have a `.git` (the eleven existing firms) were
not tried, and migrating them is out of scope. Snapshots are kept forever until
a retention policy is decided.
